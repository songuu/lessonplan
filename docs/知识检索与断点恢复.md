# 知识检索、质量重试与 Worker 恢复

知识库与原来的个人教案库分开：个人教案库继续提供写作风格参考；“知识库管理”维护本次备课可以检索的教学资料。

## 教师操作

在“知识库管理”创建知识库，上传 PDF、DOCX、Markdown（.md/.markdown）或 UTF-8 文本。文档通过后台 thumbnail 队列解析和分块，界面显示等待、解析中、可检索或失败。扫描 PDF 和旧版 DOC 仍需先转换；解析失败可重新建立索引，也可删除文档。

选择文档可以分页查看片段；输入检索词可测试召回，结果保留知识库名称、原始文件名、片段序号及匹配分数。片段序号在接口内从0开始，界面从1开始显示。所有列表、检索、片段与变更均校验当前教师及租户所有权。

新建教案默认使用当前教师的全部知识库，也可指定部分或明确停用。生成前将相关片段及出处冻结进 `knowledge_context_snapshot`，一键和结构化模型都接收同一资料快照。后来删除或更新知识文件不会修改已创建教案的引用；教案页面可查看这次使用的来源。

当前召回方式为中文双字词、英文词与 BM25 关键词相关性检索；无需额外 embedding 密钥。它不等同于向量语义检索，不会虚构无匹配的资料。最多取6个相关片段，并设置检索候选上限，超限明确要求缩小知识库或检索词范围。知识材料仅作为用户资料传入，不提供系统指令或工具执行权限。

## 知识接口

接口均带 `/api/v1` 前缀并使用现有 Bearer 登录认证；成功响应由 `data` 包装，越权资源返回404。以下 ID 均由服务端生成。

| 接口 | 输入与返回 |
|---|---|
| `GET /knowledge-bases`、`POST /knowledge-bases` | 列表含资料数量；创建传 `title`、`description` |
| `PATCH /knowledge-bases/{id}`、`DELETE /knowledge-bases/{id}` | 编辑名称/说明，或删除知识库并取消在途解析 |
| `GET /knowledge-bases/{id}/documents`、`POST /knowledge-bases/{id}/documents` | 上传使用 multipart `file`；返回文档状态及解析 `run_id` |
| `GET /knowledge-documents/{id}`、`DELETE /knowledge-documents/{id}` | 查询解析状态，或删除资料及可检索片段 |
| `POST /knowledge-documents/{id}/reindex` | 重新建立索引；在途解析返回409 `RUN_ACTIVE` |
| `GET /knowledge-documents/{id}/chunks?offset=0&limit=20` | 返回 `items`、`total`；单页最多100项 |
| `POST /knowledge-bases/{id}/search` | 传 `query`、`top_k`（1..20）；返回 `items`、`method=lexical_bm25` |

片段含原文、文档/知识库 ID 与名称、`ordinal`、内容 hash；检索另含 `score`。不返回文件存储路径。创建两种教案的输入均可传 `knowledge_base_ids`：省略或 null 为当前教师全部知识库，空数组明确停用，最多指定50个；后续模块沿用草稿已冻结的来源。

## 质量失败重试

质量修正包住“模型调用 → 解析 → Schema → 安全规范化 → 业务质量门”。蓝图、正文模块、大纲、单个课堂活动、润色候选和后台审查均采用有界尝试；默认允许额外1次修正，可配置 `QUALITY_RETRY_LIMIT=0..3`。

修正仅携带受控失败代码，不把内部异常或危险原文再次发送给模型。普通公式渲染告警保留源码，不触发重生；手工编辑保存仍是纯校验，不会自动调用模型。外层不会对所有异常无差别重试；持久回执模式中，超时、连接中断、5xx或不完整响应等结果不确定错误不会自动切备用模型，明确失败才可按Gateway策略切换。事件或 checkpoint 写入错误必须直接中止，不能冒充模型质量错误。

一键正常路径仍为一次模型调用，格式回退保留 Markdown → JSON → 分模块策略；质量不合格时只修正失败模块。教学过程只修正当前失败环节，保留此前环节。SSE 告知重试次数与范围，仅替换废弃的临时内容；恢复单环节不会把整个教学过程计为完成。

调用开始前先保存预算和稳定 call_id；每次尝试与质量结果进入持久账本。Worker 恢复后沿用已用额度，不重新获得完整重试次数。最终 CallLog 区分传输结果与 `validation_outcome`，因此“传输成功但质量失败”不会被记成模型网络故障。

## 模块级断点

数据库 `ai_run_checkpoints` 保存蓝图、完整模块、单活动、候选和预算。临时 `module_done` 不是断点：只有完整边界且通过质量门的内容才可持久复用。持久回执模式中，一键正文仍实时流式显示，但先独立保存完整原始响应，再校验并保存各模块断点；活动在单环节响应和质量门通过后保存，无需等整个任务完成。先前2026-10-16演示在流闭合模块时就保存断点，属于0005之前的行为。

恢复前校验输入、模块配置、已确认依赖、大纲、知识与风格快照、受控资产指纹；Runtime 再校验恢复正文。存在不同指纹则以 `CHECKPOINT_CONTEXT_CHANGED` 明确失败并保留原账本，不静默清空预算。正式模块版本仍在全部结果通过后，由事务统一提交。

## 执行权与重投

Run 使用 `execution_epoch`、`lease_owner`、`lease_expires_at` 与 `heartbeat_at` 标识当前执行者。默认租期30秒，每10秒独立续租，最多恢复3次；心跳间隔必须短于租期。数据库时间在获取锁之后读取，避免锁等待让已过期的执行者复活。

模块、事件、候选、导出文件指针、解析结果和终态写入都检查执行批次、所有者、状态及有效租约。HTTP 取消或删除可撤销执行权；旧 Worker 即使晚到，也不能覆盖新尝试或写重复终态。

维护 Worker 发现过期任务后，在同一事务中增加 epoch、保留断点、转回 queued 并记录 dispatch Outbox。恢复使用新批次的稳定 ARQ job ID，绕过旧进程残留的 in-progress/result keys；不删除旧任务键后冒险复用。Run ID 与 SSE sequence 保持不变，客户端可继续断点补发。

总时间预算从第一次 started_at 累计。恢复、重试次数或调用预算耗尽后，明确收口唯一失败终态。取消的任务不会恢复。0005起，完整模型响应先独立提交到 `llm_invocations`，恢复时沿用原调用身份和质量尝试，重放不消耗新调用额度；没有可靠回执的调用以 `LLM_OUTCOME_UNKNOWN` 失败并告警，禁止自动重发。调用恰好一次仍依赖Provider的可验证幂等或查询能力；当前未宣称支持。正式版本和终态保持唯一。完整设计与故障窗口见[模型调用回执与恢复](模型调用回执与恢复.md)。

配置入口为 `.env` 的 `QUALITY_RETRY_LIMIT`、`RUN_TIMEOUT_SECONDS`、`WORKER_LEASE_SECONDS`、`WORKER_HEARTBEAT_SECONDS`、`WORKER_RECOVERY_LIMIT`、`KNOWLEDGE_SEARCH_MAX_CHUNKS`，示例默认值分别为1、300、30、10、3、10000。修改后重启 API 与 Worker。

本地 `scripts/run_local.py` 会重启异常退出的 Worker，每类最多3次，防止崩溃热循环；API 退出则停止整组。只操作当前启动器持有的进程，不按历史 PID 文件强行终止进程。Docker 环境继续使用各服务自身的重启策略。

## 验证方式

自动回归包括私有资料隔离、空检索、来源快照、删除/取消与解析竞态、质量失败与预算耗尽、回调异常、部分模块及活动恢复、租约锁等待、两个维护者竞争、旧执行者写入拒绝、累计时间预算与唯一版本/终态。

`scripts/check_worker_recovery.py --real-model` 用合成教师与数学资料创建真实任务；至少两个模块断点落库后输出 `CHECKPOINT_READY`。操作员必须核对本地启动器、Worker 可执行文件、完整命令行、启动时间，再单独执行受控硬停止，并记录 `kill-receipt.json`。观察脚本本身不杀进程；它要求实际 PID 更换、同一启动器实例、真实非 mock 模型回执、断点 hash 不变、7个正式版本、唯一成功终态和连续 SSE 才能通过。

进程硬 kill 期间，文件存储与数据库无法原子提交，可能留下没有业务指针的临时对象；正常异常路径会补偿。API 取消保留 checkpoint 中的调用账本，Provider 在途请求的最终用量仍未知。这些边界不会使旧 Worker 获得正式写入权限。

2026-10-16在本地Docker PG17/Redis8.4及真实 `deepseek-flash` 上已通过实际硬停止：两个模块断点后终止Worker，自动重启、epoch增加1，仅生成缺失内容，原断点ID/hash保持不变。最终7个正式版本、1567条连续SSE及唯一成功终态。具体证据和并发回归见[验收记录](verification.md#追加验收独立知识库质量重试与模块断点2026-10-16)。
