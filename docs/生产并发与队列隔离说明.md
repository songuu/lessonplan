# 队列、预算与恢复

| ARQ队列 | WorkerSettings | max_jobs |
|---|---|---:|
| lesson:one-click | OneClickWorkerSettings | 8 |
| lesson:structured | StructuredWorkerSettings | 3 |
| lesson:module-polish | ModulePolishWorkerSettings | 6 |
| lesson:export | ExportWorkerSettings | 4 |
| lesson:thumbnail | ThumbnailWorkerSettings | 4 |
| lesson:internal-review | InternalReviewWorkerSettings | 2 |
| lesson:maintenance | MaintenanceWorkerSettings | 2 |

API只创建Run/Outbox并投递，生产不在HTTP协程运行模型。Run创建先flush，再写dispatch Outbox，同事务提交；首批稳定job_id为run-{UUID}，恢复批次为run-{UUID}-e{epoch}。enqueue返回None仅在精确job receipt可读且args匹配时算复用，其他情况收口QUEUE_UNAVAILABLE。

Worker通过queued→running条件更新认领，并持有epoch/owner/数据库时钟租约；写入必须验证仍有执行权。重复投递不重复写版本/事件/文件。业务默认300s，从首次started_at累计，恢复不会重新获得完整时长；ARQ外层330s，为写终态留30s；容器grace340s。deadline返回WORKFLOW_TIMEOUT，与用户cancel和WORKER_INTERRUPTED分开。

Maintenance每15s对账pending Outbox、published但queued的丢失job及租约过期的running。运行超预算或恢复次数耗尽才失败收口；允许恢复时原子增加epoch、保留断点并通过Outbox投递新批次，旧Worker不能提交。Redis任务已存在则复用；失踪或已有过时结果的Job按新批次投递，不删除旧ARQ键冒险重用。Outbox领域发布至少一次，RedisStream消费者以event_id去重。文件删除使用同一Outbox补偿。

SSE事实源为数据库，Redis PubSub仅传changed唤醒，通知只在commit后发送。Redis中断自动退回数据库轮询，Last-Event-ID精确重放；每轮释放数据库session，连接结束释放PubSub。

健康语义：/live仅进程；/ready检查数据库可连且已有users schema、ARQ模式Redis可连；/health加七类Worker心跳与depth。inline明确标记演示模式，不证明真实队列或Provider。生产容量仍需结合Provider额度、DB连接池与文件Worker CPU压测，不能把本机测试并发数视为容量承诺。

## 独立进程与断线恢复演示（2026-10-16）

入口为`scripts/demo_arq_sse.py`。使用隔离的PostgreSQL16.15（15432端口、lesson_test数据库）和Redis7.4.5（16379端口、事前为空的DB5），API、one-click Worker、structured Worker各自运行在独立进程。本轮实际API PID25536、Worker PID12600/32760，驱动PID26696；没有修改8000端口已有应用。模型明确为本地mock，增量增加60ms延时，以观察真实断线区间。

### 演示1：HTTP生命周期与后台任务解耦

1. 先启动API，暂不启动Worker。向`POST /api/v1/lesson-drafts/generations/one-click`提交合成教师请求。
2. HTTP在71ms返回`draft_id/run_id`。独立数据库查询得到`Run.status=queued`、正式版本数0、dispatch Outbox为published；Redis中的稳定`run-{run_id}` Job仍为queued。这时根本没有Worker进程，所以HTTP返回没有等待模型执行。
3. 同一请求再次提交，返回相同Run，不会创建第二次生成。
4. 启动独立Worker，`queued→running`条件更新认领任务。ARQ执行`execute_run`，再进入`WorkflowExecutor.generate`和`LessonRuntime.generate`。完成后数据库有7个正式模块版本及唯一完成终态。

容量限制来自Worker配置：one-click为8、structured为3；这些是单Worker进程的并发上限，并非本次测得的吞吐量。

### 演示2：执行链路与SSE通知链路分离

| 时刻 | 客户端 | PostgreSQL Run | PG最新事件序号 |
|---|---|---|---:|
| API返回 | 尚未订阅 | queued | 0 |
| 收到2条正文增量后主动关闭SSE | Last-Event-ID=5 | running | 5 |
| 断开约650ms后独立查询 | 已断开，游标仍为5 | running | 16 |
| 携带Last-Event-ID=5重连并读完 | 收到6..60，共55条 | completed | 60 |

前后两段事件合并后严格为1..60，无缺口、无重复；终态仅一条。独立Pub/Sub观察者实际收到的是`changed`，没有收到正文。读取该唤醒时，PG已经有第16条事件。因果顺序由`WorkflowExecutor.emit`中`session.commit()`之后才调用`Dispatcher.notify`保证。

实际一键Run为`aecb8b0b-b9f3-44a8-bebf-62c1853512df`，通道为`lesson:run:{run_id}`。对应SSE请求：

```http
GET /api/v1/generation-runs/aecb8b0b-b9f3-44a8-bebf-62c1853512df/events
Authorization: Bearer <当前教师token>
Last-Event-ID: 5
```

SSE接口从`ai_generation_events`查询`sequence>5`，按序读取并发送，不是直接转发Pub/Sub正文。事件`data`包含`run_id`、`sequence`和payload；模块增量另外包含`module_id/delta/is_temporary`。前端`watchRun`按id去重、携带断点重连；终态后读取正式草稿。若GET Run已经终态，前端直接读取正式版本，不再播放旧增量。

临时`module_done`只是该模块初稿流完；正式版本和最终替换增量在质量检查后提交。一键模式的正式模块结果在最后事务中提交，不能把每个临时模块完成事件当成正式落库。

### 编排与调用次数的实际边界

- 当前类名是`WorkflowExecutor`（事务和任务状态）与`LessonRuntime`（AI工作流），没有名为`PlanOrchestrator`的类。
- 一键生成默认使用确定性输入蓝图，加一次LLM调用输出多个模块，再逐模块校验。本轮7模块对应1条调用记录；解析失败才走JSON/分批兜底。
- 结构化演示：首次蓝图+教学目标2次调用；教师确认后，大纲复用蓝图1次调用；再确认大纲，3个活动环节各1次调用，共3次。它们是3个独立Run，跨Run复用已持久化蓝图，不等于同一Run中自动跳过教师确认。
- 后续实现增加独立私有知识库与BM25检索，创建草稿时冻结知识片段及出处并传入两种生成流程；个人教案继续提供独立风格摘要。
- 格式/业务校验由SafePatch、Schema和质量门执行，失败单元可在累计调用、时间和修正次数预算内重新生成；普通渲染告警不重试，Provider主备故障仍由Gateway处理。
- 历史进度已经持久化在PostgreSQL，断线完整补发无需先升级Redis Streams。已有Redis Stream主要用于Outbox领域事件，与该SSE历史源不同。
- 后续实现持久化已验证蓝图、完整模块和活动断点；租约恢复后只生成未完成单元。未闭合Token不作为可复用断点，外部模型调用不承诺严格exactly-once。恢复机制与硬停止实测见[知识检索与断点恢复](知识检索与断点恢复.md)。

### 重复运行与证据

在专用PG/Redis已启动后，选择一个事前为空的Redis DB：

```powershell
$env:LESSON_EXTERNAL_DATABASE_URL='postgresql+asyncpg://lesson_test@127.0.0.1:15432/lesson_test'
$env:LESSON_EXTERNAL_REDIS_URL='redis://127.0.0.1:16379/4'
uv run python scripts/demo_arq_sse.py
```

脚本拒绝非回环地址、默认端口、非lesson_test库及非空Redis DB，不执行flush/drop/truncate。每轮业务使用随机ID，保留已有记录。证据中的Redis连接只保存主机/端口/DB，省略凭证。演示有90秒总截止时间；自建子进程先协作退出，超时仅终止由Popen直接持有的子进程句柄。

本轮历史证据在本机`.cache/arq-sse-demo/c5a3f2a1c99841fbbfed78702e47583f/evidence.json`，3个子进程均协作退出且退出码0；`cleanup_errors=[]`。该演示未覆盖真实Provider/COS或Worker崩溃，基础数据库与Redis已按身份核验后停止。后续Docker真实模型与模块断点硬停止验证见[验收记录](verification.md)；没有生产容量证据。
